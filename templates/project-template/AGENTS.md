# AGENTS.md
> 项目级 AI 指令文件。各主流 AI 编码工具(Claude Code / Codex / Cursor 等)进入项目时优先读取本文件。
>
> **本文件内联了硬约束原文，不是指针。** 无论主 agent 还是子 agent，动手写代码前必须读完本文件；不得以"稍后去读 skill"代替。完整细则见 charles-coding Skill 各分册，但下方清单即为交付红线。

## 0. 交付红线(必须满足，否则不算完成)
- 交付前必须跑 `make verify`(先规范校验 `scripts/check.sh`，再跑测试 `scripts/test.sh`)，**全绿才算完成**。
- 测试必须实跑并全部通过，禁止"看起来对"就交付。
- 代码提交到 `agents/feature/<描述>` 分支，禁止直接推 `main` 或发起 PR，禁止任何 AI 联合署名。
- **证据驱动**：凡事实或技术判断，先查实相关源码/文档/命令输出再作答，结论必须附依据(文件:行号、实跑输出、官方文档)；不确定就明说、点出缺口，绝不编造(简短交互如"继续"不在此列)。

## 1. 命名硬约束(高频踩坑，逐条对照)
- **Java / Kotlin / TS**：请求(入参) `XxxReqVO`、响应(出参) `XxxRespVO`、内部/跨服务 `XxxDTO`。细分：新增/保存 `XxxSaveReqVO`、分页 `XxxPageReqVO`。**禁止**裸 `XxxVO`、`XxxDTO` 直接当请求/响应暴露给前端。
- **Go**：请求 `XxxRequest`、响应 `XxxResponse`，内部 `XxxDTO`。
- **Python(FastAPI + Pydantic)**：`XxxCreate` / `XxxUpdate` / `XxxResponse` / `XxxFilter`。
- **变量/函数见名知义**：禁止单字母(`i`/`j` 仅限循环索引)、`tmp`/`data`/`obj`/`item1` 等无意义名；遍历用 `for (Order order : orders)` 而非 `for (Order o : orders)`。
- **函数名 = 动词 + 名词**，动词与注释里的中文动作词一一对应(获取 get / 查询 query / 校验 validate / 核验 verify / 组装 build / 解析 parse / 降级 fallback ...)，**同一动作全项目只用一个动词**(定了 `get` 就别在别处写 `fetch`/`obtain`)。
- **禁止隐喻或口语命名**：`envelope`/`box`/`stuff`/`thing`/`magic`/`doIt`/`doSomething`/`handleStuff`，以及编号凑数名 `data1`/`item2`；`scripts/check.sh` 检查四会拦截 `tmp`/`obj`/`foo`/`stuff`/`doIt` 这类占位名。
- **布尔用 `is`/`has`/`can`/`should` 前缀，集合用复数**；**禁止拼音混拼**(`shangpinList`/`getYonghu`)；同一概念全项目同名(不要 `productId`/`goodsId`/`itemId` 混用)。

## 2. 注释语法硬约束(高频踩坑，`scripts/check.sh` 会校验)
**多行注释一律用块/文档注释语法，禁止用连续多行 `//` 或 `#` 拼多行注释。** 单行注释才用 `//` / `#`。逐语言对照：

| 语言                                   | 多行 / 文档注释                     | 单行注释 |
| -------------------------------------- | ----------------------------------- | -------- |
| Java / Kotlin                          | `/** ... */`                        | `//`     |
| JS / TS / JSX / TSX / CSS / SCSS       | `/** ... */`(CSS 用 `/* ... */`)    | `//`     |
| Go                                     | `//`(Go doc 标准，声明级注释即使多行也用 `//`；仅文件头用 `/* ... */`) | `//` |
| Python                                 | `"""` docstring                     | `#`      |
| Vue SFC / HTML                         | `<!-- ... -->`                      | `<!-- ... -->` |
| SQL                                    | `/* ... */` 或整块 `--`             | `--`     |
| Shell / YAML / Dockerfile              | `#`(无块注释语法，唯一例外)         | `#`      |

- **块注释三段式**：`/**` 独占首行，正文每行以 ` * ` 开头，` */` 独占末行。禁止 `/** 正文 */` 挤成一行。
- **Python docstring 三段式**：`"""` 独占首行、**正文一律从第二行开始**、`"""` 独占末行(单行内容同理)。禁止 `"""摘要...` 这种正文跟 `"""` 挤在同一行的写法。统一双引号 `"""`，**禁止** `'''`。
- **禁止把单行说明写成三引号字符串**：那在 Python 里是 no-op 表达式不是注释。单行说明用 `#`。
- **说明性注释写在被说明对象的上一行**，禁止写在下方。
- **注释篇幅：正文默认 1-2 行，硬上限 3 行**(`@param` / `@return` 等标签行不计入)。禁止在注释里写背景推演、方案权衡、为什么不选另一种做法、故障复盘 -- 这些写进 `docs/modules/<系统模块>/<模块>.md` 或 commit message。
- **一条注释一行写完**：禁止把一句话折断换行，行尾不得是逗号 / 顿号 / 分号(`scripts/check.sh` 检查六拦截)。写不下说明这条注释太长，删减或改成每行一句、各自完整。
- **注释语言**：一律中文。
- **注释措辞：动作 + 对象 + 必要条件**，一句话说清做什么。动作词全项目统一(获取 / 读取 / 查询 / 创建 / 更新 / 删除 / 校验 / 核验 / 检查 / 过滤 / 转换 / 组装 / 解析 / 保存 / 限制 / 截取 / 降级 / 跳过 / 计算 / 汇总 / 对比 / 记录)，同一行为不得换着说法写。
- **禁止隐喻黑话**(信封 / 盒子 / 塞进 / 拆出 / 压成 / 喂给 / 吐出 / 搬运 / 留给下游 / 拼起来 / 灌进去 / 形状不符 / 收口 等)，`scripts/check.sh` 检查七直接 fail；落盘 / 口径 / 兜底 / 水位 / 通道 / 打包 等词非项目正式术语时也须改写。
- **抽象表达必须改成具体职责**：落一条 / 拍快照 / 种入 / 一路事件 / 人话字段 / 就地打进去 / 空转 / 吃一个报错 / 一等公民 / 哨兵 / 守门员 / 胶水层 / 承载器 / 分发器 / 魔法 / 仪式 / 管家 / 护城河 等词不得代替位置、输入、输出和行为影响；确属正式技术术语或业务术语时除外。
- **同一套措辞适用于日志文案、异常消息、用户可见提示与降级文案**，不做无谓中英混杂(`正在 live 核验` 写成 `正在核验`)。
- **删掉零信息注释**：只复述代码的注释(`// 获取 service`、`# 返回结果`)一律删除，留下的注释要说清"为什么"(为何降级 / 为何限制数量 / 为何覆盖字段)。

## 3. 文件头注释块(每个源码文件必须有)
每个源码文件顶部必须含以下三行(按上表的注释语法适配)，`scripts/check.sh` 全部校验：

```
<一到两句话说明本文件职责>
创建日期：YYYY-MM-DD
修改日期：YYYY-MM-DD
```

- **第一行直接写作用描述**：使用一到两句自然、具体的中文说明核心职责，不加"文件作用："、"文件职责："、"作用："等前缀标签，句尾不加句号。
- **描述必须准确具体**：不得只写"品牌"、"工具类"、"公共组件"等宽泛名词；不得罗列分页、创建、更新、删除、上传等全部能力；不得写架构角色、实现步骤、设计原因、修改历史、Bug 排查过程或本次变更内容。
- **日期行的冒号必须是中文全角**，禁止半角冒号。
- **已知日期必须严格使用 `YYYY-MM-DD`**；创建日期没有可靠依据时允许留空并在交付说明中列出，禁止编造。
- **创建日期只在新建文件时写入**，此后任何重构(含成批改注释)都不得改动；**修改日期**在本次真改了文件时(只改注释也算)更新为当天，未改动的文件不更新。
- 文件头**只写作用，不写实现**：禁止写实现细节、设计推演、查证结论。
- Java / Kotlin 的文件头 Javadoc/KDoc 放在**类声明上方**(文件物理顶部是 `package`/`import`)；类上有注解时放在**注解之上**。
- Python 文件首行加 `# -*- coding: utf-8 -*-`，置于文件头注释块之前。
- **例外：`.css` / `.scss` 文件不写文件头**，它们不写任何注释，见第 5 节的样式规则。

## 4. 禁用字符(纯文本规则，`scripts/check.sh` 会校验)
- **禁止**弯角引号(中文弯引号)，统一用半角 `"` / `'` 或不加引号。
- **禁止**中文长破折号(EM DASH)，统一用半角双连字符 `--`。
- **禁止** Emoji 出现在代码、注释、文档、提交信息中；需图标用 SVG 或 icon 字体。

## 5. 结构与格式硬约束
- **分层架构**：后端强制 Controller → Service → Repository，禁止跨层(Controller 不直接调 Repository)，禁止把全部逻辑写进一个文件/函数。
- **强制大括号**：所有 `if`/`else`/`for`/`while`/函数体，即使只有一行也要 `{}`；完整代码块与相邻同级语句之间留空行(`} else {` 等续接行、块内首末行不要求)。
- **禁止魔法数字**：裸数字提为文件/类顶部具名常量(`MAX_RETRY_COUNT` 等)。
- **键值/元素独占一行**：对象字面量每个键值一行带尾逗号；HTML/JSX 每个元素一行；禁止并排。
- **缩进**：默认 Tab；Python / Kotlin 4 空格、SQL / YAML / JSON 2 空格(见 `.editorconfig`)。行尾统一 LF。
- **样式不写注释**：`.css` / `.scss` 文件与 Vue SFC 的 `<style>` 块内禁止出现任何注释，含文件头；样式意图由 class 名与 CSS 自定义属性命名表达，设计决策写进模块文档。`scripts/check.sh` 检查九会拦。
- **import 排版**：顺序固定为第三方值 import、项目内值 import、全部 type import、常量与其余代码，组间空一行；type 一律用 `import type`，**禁止把 type import 混进值 import 中间**。`scripts/check.sh` 检查十会拦。
- **元素多行书写**：模板里所有元素属性各占一行、文本单独占一行、结束的 `>` 或 `/>` 单独占一行，同一父元素下相邻子元素之间空一行；只有组件自闭合，`div`、`span`、`iframe`、`button` 等原生标签永远成对出现。TS/JS 里同一数组的相邻元素之间空一行，对象内部键值对不空行。排版只改格式，不动顺序、命名、属性与业务逻辑。
- **单一入口**：一项能力对外只暴露一个入口模块，底层实现不许被入口之外的地方直接 import(例如认证只能经由 `composables/useAuth`，不许直接引 `utils/auth`；Controller 不许直接引 Mapper)。受保护关系写在项目根 `.import-boundaries`，`scripts/check.sh` 检查八会拦。绕过入口的调用通常也能跑通，但入口层的缓存、鉴权刷新、错误处理会对它全部失效。

## 6. 代码编写与组织规范
以下规则默认适用于所有新写和修改的源码，不需要用户另行提出"整理代码"。

- 静态 import 位于语言允许的顶部区域；动态 `import()` 保留在实际加载位置。
- 同类类型、常量、状态和配置优先集中定义，但不得改变初始化顺序、顶层副作用和注册顺序。
- 文件按文件头、package/静态 import、类型、常量与配置、组件或类定义、状态、派生状态、初始化与生命周期、业务方法、最终提交或保存操作的顺序组织。
- 业务方法按页面展示顺序或执行流程排列；`submit`、`save`、`launch` 等最终操作放在相关流程之后。
- Vue `<script setup>` 优先按静态 import、类型、常量、组件定义、状态、computed、生命周期、业务流程方法、最终提交方法排列。
- 函数参数列表、调用参数、对象字面量、数组字面量和返回对象内部不得插入大段解释性注释。
- 删除历史 Bug、调试过程、实测记录和零信息注释；有业务含义的常量、类型和字段按需注释，不机械补注释。
- 修改已有代码时，无法证明移动前后行为一致就保留原位置。
- 用户只要求整理代码或统一注释时，禁止修改业务逻辑、接口调用、数据结构、返回值、字段名、函数名、变量名、API 参数和组件交互；禁止借机合并函数、抽取工具函数、删除业务代码或修复未获授权的 Bug。
- 委派实现任务时，任务说明必须内联代码组织规则；整理已有代码时还要内联允许修改项、禁止修改项和验证要求。
- 完成后检查 diff，并实跑格式化、规范校验和相关测试。

## 7. 开发交流
- 默认使用自然、专业的简体中文；代码、命令、API、文件路径和正式技术术语保持原样。
- 先说结果，再提供必要原因、证据和影响；同一个结论只说一次，不复述用户需求。
- 减少"让我先看看""接下来我将"等过程播报，只在任务较长、遇到阻塞或平台要求时发送有实际信息的简短进度。
- 不使用"一等公民""守门员""胶水层"等抽象或比喻表达代替具体职责，改为说明位置、输入、输出和行为影响。
- 代码修改完成后默认只说明改了什么、验证结果和确实存在的风险；用户明确要求报告或详细分析时再展开。
- 不展示工具名、执行器标签、内部状态和推理过程。
- 需求清晰、修改可逆且没有真实产品取舍时直接执行；产品、架构、兼容性、破坏性操作或权限扩张仍须确认。

## 8. 变更类型闸门(动手前先判定本次属于哪一类)

| 变更类型 | 模块文档 | 测试要求 | 编码前置 |
| --- | --- | --- | --- |
| 新模块 / 新功能 | **必写** `docs/modules/<系统模块>/<模块>.md`，评审通过后再编码 | 用例文档 + 实跑全绿 | 需求边界、入参出参、异常场景逐个问清，没问清不许开写 |
| 需求变更 | **改已有文档**对应小节，失效行为标注作废 | 改用例 + 全量回归 | 确认影响面、上下游依赖与兼容性 |
| Bug 修复 | 不写；文档与实现不符时回改 | **先写复现测试并确认它失败，再改实现**；测试保留进 `test_cases/<模块>/regression/` | 定位根因，禁止只治症状 |
| 重构 | 不动 | 现有测试全绿，**禁止修改断言、删用例、放宽阈值** | 证明改动前后行为等价 |
| 依赖升级 / 配置 | 不写 | 冒烟通过 | 记录版本变化与已知风险 |

- 判定不了就按更严格的一档执行。
- 分支一律 `agents/feature/*`，变更类型只决定闸门，不决定分支名。

## 9. 常用命令
```bash
make verify      # 交付前总闸门：增量规范校验 + 测试(全绿才算完成)
make verify-all  # 全量闸门：全量规范校验 + 测试(推主干与 CI 用)
make lint        # 仅规范校验，只查本次改动(禁用字符/文件头/注释语法/注释篇幅/注释黑话/必需文件/命名/模块边界/样式注释/import 排版)
make lint-all    # 仅规范校验，全量扫描
make check       # 仅跑测试
make dev         # 启动开发环境
```

> `scripts/setup.sh` 会安装 `pre-push` 钩子：推 `main` 跑全量 `verify`，推其它分支跑增量校验。云端 CI 是二次确认，本地钩子才是拦截点。

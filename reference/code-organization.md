> 新写、修改、整理或审查源码时默认使用。开始前仍须遵循 [SKILL.md](../SKILL.md) 和对应语言分册。

## 适用范围
所有新写和修改的源码都必须遵守本规范，不需要等用户单独提出"整理代码"。

本规范约束文件内各类代码的排列顺序、注释位置和阅读顺序。语言格式继续由项目现有格式化和 Lint 工具处理，不擅自切换工具或覆盖项目已有的有效约定。

## 通用排列顺序
在不改变运行行为的前提下，源码按以下顺序组织：

1. 文件头注释
2. package、静态 import 或同类模块声明
3. type、interface、enum 等类型定义
4. 常量、配置、正则和静态属性
5. 组件输入输出或类属性
6. 状态与派生状态
7. 初始化和生命周期
8. 按业务执行流程排列的方法
9. submit、save、launch 等最终操作
10. 导出声明或语言要求的收尾结构

无法应用的类别直接跳过。语言或框架对位置有强制要求时，以语言或框架要求为准。

## import
静态 import 位于语言允许的顶部区域，并由对应语言的格式化或 Lint 工具排序。不要强行改变项目已有的 import 分组风格。

动态 `import()` 属于运行逻辑，必须保留在实际加载条件对应的函数或分支中，不得为了视觉集中移动到顶部。

## 定义区
import 后集中放置同类定义，避免属性和函数无规则穿插：

- type、interface 和 enum
- 常量、配置对象、正则、Set 和 Map
- defineProps、defineEmits 等组件定义
- ref、reactive 和 composable 返回值
- computed 等派生状态

定义存在初始化依赖、顶层副作用或注册顺序要求时保留原位置，不得为了集中定义改变行为。

## 业务方法顺序
业务方法按照页面展示顺序或执行流程排列。例如业务流程为步骤 1、步骤 2、提交，相关方法也按照步骤 1、步骤 2、提交排列。

不要按照创建日期、最近修改时间或主观重要程度排列函数。公共辅助方法放在首次使用位置附近或项目已有的统一位置，避免穿插打断主要业务流程。

`submit`、`save`、`launch` 等最终操作放在相关准备、校验和转换方法之后。

## 注释位置与内容
### 文件头注释
文件头规则和各语言模板以 [SKILL.md](../SKILL.md) 的"注释规范"为准。

- 描述必须让读者直接判断文件负责什么，不得只写"品牌"、"工具类"或"公共组件"
- 只概括核心职责，不罗列分页、创建、更新、删除和上传等全部能力
- 不写架构角色、实现步骤、设计原因、修改历史、Bug 排查过程或本次变更内容
- 创建日期只在新建文件时写入；已有日期必须保留
- 缺少创建日期时先查 Git 历史，没有可靠依据时留空并在交付说明中列出
- 实际修改文件时更新修改日期；仅扫描未修改时不得更新

### 函数注释
函数和方法使用对应语言的文档注释说明职责。存在参数且参数含义不能从名称直接判断时，使用该语言的标准参数标签，例如 JSDoc 的 `@param`。

注释只说明函数职责、代码表面无法表达的业务规则，以及容易误解的参数、返回值或异常条件。不要逐行翻译实现，也不要记录历史 Bug、调试过程、实测过程、修改人员或方案推导。

### 常量、类型与字段注释
仅在名称无法完整表达业务含义或存在重要约束时添加注释。`id`、`name`、`status`、`loading` 等含义明确的字段不机械补注释。

相关常量可以共用一条说明，但注释必须放在被说明对象上方。不要为了让每一行都有注释而制造重复信息。

### 参数和字面量内部的注释
函数参数列表、调用参数、对象字面量、数组字面量和返回对象内部不得插入大段解释性注释。说明应放在对应变量定义上方、函数文档注释中，或对象构造语句之前。

只在无法通过结构和命名表达、且必须紧邻字段才能避免误用时保留简短行内注释。

### 行内注释
行内注释只解释紧邻代码且无法直接看出的业务规则。能够由函数文档注释说明时，优先放在函数注释中。

删除以下内容：

- `获取数据`、`判断是否为空`、`返回结果`等代码已经表达的信息
- 历史故障、调试记录和临时排查结论
- 已失效的 TODO 和大段注释掉的代码
- 比代码更长但没有增加业务信息的说明

## Vue 文件
Vue `<script setup>` 的具体排列顺序见 [vue.md](vue.md)。页面功能顺序属于人工判断，不加入通用正则检查。

## 修改已有代码的边界
修改已有代码时先检查声明提升、初始化顺序、顶层副作用、装饰器、生命周期注册和异步执行时机。无法证明移动前后行为一致时，保留原位置。

以下情况不得仅为满足排列顺序而移动：

- 变量初始化依赖前面已经执行的语句
- 模块加载会注册插件、修改全局状态或执行网络请求
- 顶层 `await`、动态 `import()` 或条件加载依赖当前位置
- 生命周期、监听器或订阅的注册顺序会影响结果
- 测试或框架依赖声明顺序

如果用户只要求整理代码、统一注释或调整源码顺序，只允许修改可证明不影响行为的代码顺序、格式和注释。除非用户同时明确要求修复或重构，否则禁止：

- 修改业务逻辑、接口调用、数据结构或返回值
- 修改字段名、函数名、变量名或 API 请求参数
- 改变组件交互、状态变化、异常处理或执行时机
- 合并原本独立的函数
- 抽取新的公共函数、工具类或模块
- 删除仍在使用的代码

发现 Bug、重构机会或架构问题时只记录，不在单纯整理任务中修改。交付时列出确有依据的问题，并明确说明本次未修改。

## 编写与修改流程
1. 读取项目 `AGENTS.md`、本规范和对应语言分册
2. 确认文件职责、业务流程和项目现有格式
3. 按通用顺序编写代码，存在行为依赖时保留必要位置
4. 按文件头模板和注释位置规则编写注释
5. 使用项目已有格式化工具
6. 检查 diff，确认修改符合任务范围
7. 运行规范校验和相关测试

## 交付自检
- 静态 import 是否位于语言允许的顶部区域
- 同类定义是否集中且没有改变初始化顺序
- 生命周期是否位于业务流程方法之前
- 业务方法是否按页面或执行流程排列
- 最终提交或保存操作是否位于相关业务方法之后
- 参数列表和字面量内部是否仍有大段解释性注释
- 是否仍有历史 Bug、调试过程或零信息注释
- 修改已有代码时是否误改业务逻辑、接口、数据结构、命名或交互行为
- 格式化、静态检查和测试是否实际通过
- **交付时严禁残留无用文件**：临时脚本、调试文件、废弃代码、空目录、`xxx-copy`/`xxx备份`、注释掉的大段代码等一律清理，交付物只保留真正需要的文件
- **过程产物禁止 commit**：开发过程中产生的 `spec`、`plan`、设计草稿、调研笔记、Agent 中间产物等**禁止提交到仓库**，一律写入 `.gitignore`（如 `*.spec.md`、`plan/`、`.agent/`、`scratch/` 等按项目约定），只提交最终代码与正式文档（`docs/`、`README`、`test_cases/`）
